# قرارات تقنية — نبراس

سجل القرارات التقنية المهمة المتخذة أثناء التطوير. كل قرار يُرجع إلى ما يدعمه
في حزمة الوثائق الرسمية (المرجع الوحيد للحقيقة)، أو إلى موافقة صريحة.

---

## D-001 — خط الأساس والبناء فوقه (Phase 0)
- **القرار:** يُعتمد `files/nibras-backend.zip` (المطبوع في وثيقة المعمارية §1)
  كخط الأساس المُدقق، ويُبنى المشروع فوقه دون إعادة كتابة، في مجلد العمل
  `Default Project\nibras-backend\` كجذر مستودع مطابق لهيكل المواصفة التقنية §2.
- **المبرر:** "Extend, don't rewrite" (معمارية §3)؛ الوثائق بُنيت على تدقيق هذا الكود.
- **المصدر:** Technical Architecture §1/§2، Developer Guide §3.

## D-002 — فصل المسارات إلى Blueprints مع حفظ المسارات كما هي
- **القرار:** تحويل `app/routes.py` إلى `app/routes/library.py` + `app/routes/admin.py`
  في المرحلة 0، مع **الإبقاء على مسارات المكتبة الحالية كما هي** (`/api/texts`,
  `/api/articles/...`...) دون بادئة وحدة، ودون مسارات مؤلفة.
- **المبرر:** هذا هو القرار المفتوح الذي تتركه المواصفة التقنية §3
  ("a decision to confirm before the blueprint refactor")، وقد أقرّه صاحب المشروع
  صراحةً. يحافظ على توافق `nibras.html` الحالي (API Documentation: Base URL) بلا أي كسر.
- **المصدر:** Technical Spec §2/§3؛ قرار مستخدم مؤكد (2026-08-01).

## D-003 — إعدادات البيئة (debug و CORS و مفتاح الإدارة)
- **القرار:** إضافة `app/config.py` يقرأ كل الإعدادات من متغيرات البيئة:
  - `NIBRAS_DEBUG` (وضع تصحيح Werkzeug، مُعطَّل افتراضيًا).
  - `NIBRAS_CORS_ORIGINS` (قائمة نطاقات مفصولة بفواصل؛ الافتراضي يشمل
    نطاقات التطوير المحلي وقيمة `null` لأن فتح `nibras.html` من ملف يرسل أصل `null`).
  - `NIBRAS_ADMIN_KEY` (مفتاح الإدارة المؤقت legacy).
- **المبرر:** معالجة فجوتي `debug=True` و CORS wildcard (Security Architecture §1)،
  مع عدم كسر تدفق التطوير الحالي (فتح `nibras.html` مباشرة).
- **تنبيه:** بيئة الإنتاج يجب أن تضبط `NIBRAS_CORS_ORIGINS` و`NIBRAS_DEBUG=0` صراحة.
- **المصدر:** Security Architecture §1، Architecture §10.

## D-004 — عزل قاعدة بيانات الاختبارات
- **القرار:** تُوجّه الاختبارات `app.database.DB_PATH` إلى ملف SQLite مؤقت لكل
  اختبار، وتُبذر بيانات تحكم صغيرة كلها `is_sample_data=1`.
- **المبرر:** عدم المساس بـ `nibras.db` الحقيقية، والتزام نظام العلامات النموذجية
  (Testing Strategy §3، UI/UX §3).
- **المصدر:** Testing Strategy §2/§3.

## D-005 — نطاق CI في المرحلة 0
- **القرار:** بوابة فحص محلية (`scripts/run_checks.py` يشغّل ruff + pytest)
  + قالب GitHub Actions جاهز (`.github/workflows/ci.yml`) يُفعَّل عند وجود مستودع بعيد.
- **المبرر:** لا يوجد مستضيف git/CI حاليًا؛ القرار أقرّه صاحب المشروع.
- **المصدر:** Deployment/DevOps §3، Testing Strategy §6.

## D-006 — تبعيات التطوير في ملف منفصل
- **القرار:** إبقاء `requirements.txt` لتبعيات التشغيل فقط، وإضافة
  `requirements-dev.txt` (يضم pytest وruff) لبوابة الاختبار والـ CI.
- **المبرر:** فصل بيئة التشغيل عن أدوات التطوير، مع إبقاء التبعيات مُقيَّدة
  بنطاقات متوافقة (Maintenance Guide §1).
- **المصدر:** Maintenance Guide §1، Developer Guide §4.

## D-007 — إبقاء مفتاح X-Admin-Key مؤقتًا
- **القرار:** المسارات الإدارية تبقى محمية بـ `X-Admin-Key` (legacy) خلال المرحلة 0،
  على أن تُرحَّل إلى JWT + `require_role("admin")` في المرحلة 1.
- **المبرر:** استبدال المفتاح الثابت هو نطاق المرحلة 1 (Roadmap §23 Phase 1)؛
  المرحلة 0 تُحصّن الأساس دون تغيير سلوك إدارة المحتوى.
- **المصدر:** Auth & Authorization §2.5، Roadmap Phase 1، API Documentation.

## D-008 — تضييق استثناء البحث الاحتياطي في FTS5
- **القرار:** تضييق `except Exception` في `search_articles()` إلى
  `except sqlite3.OperationalError` (خطأ صياغة FTS5) مع الحفاظ على مسار البحث
  الاحتياطي LIKE كما هو.
- **المبرر:** التقاط الأخطاء العامة يخفي أخطاء برمجية حقيقية؛ خطأ MATCH في FTS5
  من نوع OperationalError تحديدًا (Functional Spec §1: "falls back to LIKE
  matching if the FTS query fails"). لا تغيير في السلوك.
- **المصدر:** Functional Specification §1؛ قرار فرضته بوابة الفحص.

## D-009 — طباعة البذر آمنة الترميز
- **القرار:** إضافة إعادة تهيئة stdout إلى UTF-8 في `python -m app.seed` بحيث لا
  تنهار الطباعة الختامية على وحدات تحكم لا تدعم Unicode (مثل Windows cp1252).
- **المبرر:** أمر `python -m app.seed` المذكور في Developer Guide §1 يجب أن ينجح
  برمز خروج صفري في كل بيئات التطوير المحلية. لا تغيير في البيانات أو السلوك.
- **المصدر:** Developer Guide §1 (Getting Started).

## المرحلة 1 — أساس الهوية (المصادقة والتفويض)

## D-010 — تبعية التشفير: argon2-cffi
- **القرار:** إضافة `argon2-cffi>=23,<25` إلى `requirements.txt` لتجزئة كلمات
  المرور بخوارزمية argon2id، وإضافة `PyJWT>=2.8,<3.0` لسك وتوثيق توكنات JWT.
- **المبرر:** المواصفة التقنية §4 تحدد argon2id صراحةً ("argon2id ... fallback
  bcrypt only if the deployment environment makes argon2 harder to install").
  التثبيت نجح على Python 3.14/Windows فلزم الاختيار الأساسي (argon2id).
- **المصدر:** Technical Spec §4، Auth & Authorization §2.1.

## D-011 — نموذج الهوية (الجداول الخمسة)
- **القرار:** إضافة `users` و`roles` و`user_roles` و`refresh_tokens` و
  `password_reset_tokens` إلى مخطط SQLite في `database.py` (SCHEMA نفسه)،
  وفق قاعدة البيانات §2. جدول `roles` مكوَّن من `code` (فريد) و`name`؛
  تحديد الأدوار المهنية التي تبدأ بـ `pending_verification` محسوم في كود
  الخدمة (`PROFESSIONAL_ROLES`) لا في قاعدة البيانات (مصدر واحد للحقيقة،
  بلا تكرار). أُضيفت فهارس على مفاتيح `user_id` الأجنبية للحذف التسلسلي
  والبحث الفعال.
- **توضيح الأدوار المهنية (§2.1):** يُعامَل كل دور مهني/مؤسسي على أنه يتطلب
  تحققًا فيبدأ `pending_verification`، وهي: lawyer, notary, adoul,
  judicial_commissioner, sworn_translator, judicial_expert, company,
  institution. أما citizen وstudent فتُفعَّل فورًا، وadmin يُمنح داخليًا
  فقط (D-016). هذا التحديد قرار تنفيذي لأن الوثيقة تشترط المعاملة دون أن
  تعدد القائمة حرفيًا.
- **المبرر:** قائمة الأدوار مغلقة وثابتة (§1)؛ تخزين الأدوار في جدول موثَّق
  يسمح بعلاقات متعددة مستقبلاً مع الحفاظ على مصدر واحد للحقيقة.
- **المصدر:** Auth & Authorization §1/§2، Database Design §2.

## D-012 — إيقاع الدوران والإبطال للتوكنات
- **القرار:** توكن التحديث (refresh) عشوائي من 48 بايت يُسلَّم في جسم الاستجابة،
  ويُخزَّن مجزَّأً بـ SHA-256 في `refresh_tokens`؛ يُدار (rotate) عند كل استخدام
  فيُحذف القديم ويُنشأ جديد في نفس المعاملة؛ يُبطَل عند تسجيل الخروج وعند تغيير
  كلمة المرور؛ JWT وصول قصير العمر (افتراضي 15 دقيقة).
- **المبرر:** المواصفة التقنية §4 (تخزين مجزأ، دوران، إبطال) + قرار صاحب المشروع
  بتسليم التوكن في جسم الاستجابة لأن الواجهة الحالية file:///CDN تمنع الكوكيز.
- **المصدر:** Technical Spec §4؛ قرار مستخدم مؤكد (2026-08-01).

## D-013 — استعادة كلمة المرور بواجهة مرسل بريد قابلة للاستبدال
- **القرار:** تنفيذ التدفق الآن (جدول `password_reset_tokens` + نقطتا
  request/confirm بزمن صلاحية افتراضي ساعة واحدة) عبر واجهة `Mailer`
  قابلة للاستبدال؛ التنفيذ الافتراضي يطبع رابط الاستعادة في سجل الخادم
  (وضع التطوير) لأن مزود البريد غير محدد في الوثائق.
- **المبرر:** وثيقة المصادقة والتفويض §2.6 توجب الاستعادة بزمن صلاحية وربط
  المستقبل بمزود حقيقي دون تغيير التدفق. قرار صاحب المشروع: التنفيذ الآن.
- **المصدر:** Auth & Authorization §2.6؛ قرار مستخدم مؤكد (2026-08-01).

## D-014 — استبدال X-Admin-Key كليًا بصلاحيات JWT
- **القرار:** إزالة `config.ADMIN_API_KEY` و`require_admin_key`؛ النقطتان
  الإداريتان (`/api/admin/...`) صارتا محميتين بـ `require_role("admin")`
  عبر مصادقة Bearer JWT؛ رأس `X-Admin-Key` أصبح مرفوضًا (401).
- **المبرر:** هذا هو نطاق المرحلة 1 المعلن (§2.5): "الحماية الإدارية الحالية
  بمفتاح X-Admin-Key تُرحَّل إلى JWT + دور admin"، مع نقش الـ UI لاحقًا.
- **المصدر:** Auth & Authorization §2.5، Roadmap Phase 1، Technical Spec §2/§4.

## D-015 — سر توقيع JWT ومعدل الطلبات
- **القرار:** `JWT_SECRET` يُقرأ من `NIBRAS_JWT_SECRET`؛ عند غيابه يُولَّد سر
  عشوائي لكل إقلاع (آمن للتطوير، تنتهي الجلسات عند إعادة التشغيل) مع تنبيه
  في وضع التطوير. حد معدل الطلبات على نقاط المصادقة والاستعادة في الذاكرة
  (لكل عنوان IP + نقطة) بقيم قابلة للتعديل.
- **المبرر:** لا توجد قيمة سر ثابتة في الكود (Security §1)؛ معدل الطلبات على
  المصادقة والاستعادة مطلوب (وثيقة 12) — تنفيذ الذاكرة يكفي للنشر أحادي
  العملية ويُسجَّل نقله إلى مخزن مشترك عند التوسع.
- **المصدر:** Security Architecture §1، وثيقة 12، Auth & Authorization §2.6.

## D-016 — إنشاء أول حساب مسؤول عبر CLI فقط
- **القرار:** الدور الإداري يُمنح حصريًا عبر `python -m app.create_admin`
  (يقرأ `NIBRAS_ADMIN_EMAIL`/`NIBRAS_ADMIN_PASSWORD`/`NIBRAS_ADMIN_NAME`)
  أو دوال الخدمة الداخلية؛ التسجيل العام يرفض دور admin برسالة صريحة (403).
- **المبرر:** منح امتياز المسؤول عبر واجهة عامة ثغرة؛ الخط المسيطر يتطلب
  امتلاك بيئة التشغيل (§2.5 تشديد التمكين) ولا يعتمد على بيانات بذر عامة.
- **المصدر:** Auth & Authorization §2.5، Security Architecture §1.

## المرحلة 2 — لوحة الإدارة (إدارة المحتوى + طابور التحقق)

## D-017 — نطاق المرحلة 2 وترتيبها مقابل Roadmap
- **القرار:** المرحلة 2 في خطتنا التنفيذية هي **لوحة الإدارة** بالنطاق
  القابل للتطبيق الآن: إدارة محتوى المكتبة (النصوص والمواد) + طابور التحقق
  من الطلبات المهنية، مع واجهة إدارة داخلية منفصلة (`admin.html`).
  النطاقات الأخرى في وثيقة 20 (§3.3–3.6: الوساطة، الفواتير/الاشتراكات،
  الإعلانات، التحليلات) تُؤجَّل إلى حين وجود وحداتها (community، billing،
  ads) لأنها لا تملك بيانات/جداول حاليًا.
- **المبرر:** ترقيم Roadmap §23 يضع لوحة الإدارة في "Phase 1" و Phase 2
  للقيمة المميزة (AI/حاسبات/فواتير)، بينما أمر صاحب المشروع "ابدأ المرحلة
  التالية" بعد اكتمال الهوية قصدها لوحة الإدارة. الوثيقة 20 نفسها
  (قسم "Why It's P1, Not P2") تنص على بناء اللوحة بالتوازي مع الوحدات
  التي تديرها، لذا يُقدَّم بناء اللوحة لخدمة ما هو قائم. هذا القرار يُوثِّق
  التوفيق دون إهمال أي من الترتيبين.
- **المصدر:** Admin Panel Spec §1/§2/§3؛ Roadmap §23؛ قرار مستخدم مؤكد.

## D-018 — إضافات النماذج: سجل التدقيق وسبب الرفض
- **القرار:** إضافة جدول `admin_audit_log` (admin_id، action، target_type،
  target_id، details، created_at) بعمود `admin_id` بسلوك `ON DELETE SET NULL`
  لإبقاء السجل للمساءلة حتى لو حُذف حساب المسؤول، وإضافة عمود
  `user_roles.rejection_reason` لتخزين سبب رفض التحقق. تُطبَّق إضافة العمود
  على قواعد البيانات القائمة عبر ترحيل خفيف idempotent في `init_db`
  (`_ensure_column`).
- **المبرر:** وثيقة الأمان §8 توجب تسجيل الإجراءات الإدارية (المسؤول،
  الفعل، الهدف، التوقيت) لكن وثيقة قاعدة البيانات 06 لا تُعرّف جدولًا له،
  ووثيقة المصادقة §3 توجب الرفض مع سبب دون تحديد مكان تخزينه — هذان أدنى
  تنفيذين يفيان بالمتطلبين الموثقين.
- **المصدر:** Security Architecture §8؛ Auth & Authorization §3؛ Database Design §2.

## D-019 — نقاط نهاية الإدارة الجديدة ومعرف طابور التحقق
- **القرار:** إضافة عمليات تعديل/حذف للنصوص (`PUT`/`DELETE /api/admin/texts/<id>`)
  والمواد (`PUT`/`DELETE /api/admin/articles/<id>`) مع استمرار شكل الاستجابة
  الموثق `{id, message}`، ونقاط طابور التحقق
  (`GET /api/admin/verification-queue`,
  `POST /api/admin/verification/<user_id>/approve|reject` حيث `<id>` هو معرف
  المستخدم لعدم وجود جدول طلبات مستقل)، وحذف النص يحذف مواده تسلسليًا
  (ON DELETE CASCADE + مشغّلات FTS). كل هذه المسارات محمية بـ
  `require_role("admin")` وتُدوَّن في `admin_audit_log`.
- **المبرر:** وثيقة 20 §3.1 تنص على "create/edit" للنصوص والمواد، ووثيقة API
  تعدد مسارات طابور التحقق وتلتزم بشكل `{id, message}` للمعدِّلات؛ مسارات
  PUT/DELETE غير مرقمة في وثيقة API لذا اتبعنا اصطلاح REST المتسق مع
  المسارات القائمة. الحذف مدعوم بتصميم المخطط (مشغّلات FTS لـ DELETE و
  حذف تسلسلي) ويُسجَّل كإجراء إداري.
- **المصدر:** API Documentation §Admin؛ Admin Panel Spec §3.1/§3.2؛
  Security Architecture §3/§5/§8.
