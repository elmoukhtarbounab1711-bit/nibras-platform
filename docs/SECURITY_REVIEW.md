# مراجعة أمنية شاملة — نبراس (المرحلة 11)

التاريخ: 2026-08-02 | النطاق: خادم `nibras-backend` (Flask + SQLite + JWT)
المرجع: مبادئ وثيقة `12_Security_Architecture.md` (الأقسام §7 و §8) و
`21_Testing_QA_Strategy.md` و `22_Deployment_DevOps.md`.

## المنهجية
1. قراءة الكود مرورًا على كل خدمة (`services_*.py`) ومساراتها وطبقة المصادقة
   والتخزين.
2. فحص حقن SQL، عبور المسارات، كشف الأسرار، تعرض نهايات المصادقة، حدّ المعدل.
3. تحقق آلي (اختبارات + تشغيل مباشر) من السلوك الآمن.
4. توثيق ما تم إصلاحه في هذه المرحلة وما أُجِّل.

## الملخص التنفيذي
- لا ثغرات **حرجة/عالية** مفتوحة. جميع الاستعلامات تمرّ بمعاملات `?`؛
  والأجزاء المركَّبة ديناميكيًا قوائم بيضاء ثابتة (أعمدة/جداول) لا يُدخلها المستخدم.
- ملفات الرفع تُخزَّن بمفاتيح عشوائية ولا يُخدم منها إلّا عبر `os.path.basename`
  (بلا عبور مسار).
- كلمات المرور argon2id، ورموز التحديث/إعادة التعيين مخزّنة مُجزّأة (sha256)،
  ورموز الدخول JWT قصيرة الأجل.
- في هذه المرحلة أُضيفت رؤوس أمن قياسية، وسجلّات مهيكلة مع تعمية الحقول
  الحساسة، ونقطة جاهزية، ونسخ/استعادة موثّق، وحمل/إجهاد تم اختباره.

## الأدلة (أمثلة موضعية)

### حقن SQL — لا قيم من المستخدم في التركيبة
- `app/services_admin.py`: بناء `UPDATE ... SET` من قائمة مفاتيح ثابتة،
  والقيم كلها `?`.
- `app/services_analytics.py:26-56`: `_role_placeholders()` يبني `IN (?...)`
  من ثوابت `PROFESSIONAL_ROLES`، وأسماء الجداول في `_count_role` ثوابت.
- `app/services_community.py` و `services_professionals.py`: قوائم `IN`
  تُبنى من عدد `?` والمجتمع/المحترفون يمرّون كمعاملات.

### عبور المسار — لا ثغرة
- `app/services_professionals.py:289,316` و `app/services_marketplace.py:120`:
  كل قراءة/حذف ملف عبر `(_uploads_dir() / os.path.basename(storage_key))`.
- مفتاح التخزين مولّد عشوائيًا عند الرفع (لا يُؤخذ اسم الملف الأصلي).

### المصادقة والتشفير
- `app/services_auth.py:24,97-104`: argon2id عبر passlib `PasswordHasher()`.
- `app/services_auth.py:114-116`: تجزئة الرموز المخزنة بـ sha256.
- `app/services_auth.py:277,284`: JWT بـ `config.JWT_SECRET`
  وخوارزمية مضبوطة، وTTL قصير (افتراضي 15 دقيقة) + تحديث منفصل.
- `app/middleware/auth_middleware.py:63-69`: `require_role` يتحقق من
  `has_active_role` فعلًا.

### الأسرار
- `app/config.py`: كل السرية عبر `NIBRAS_*`؛ `NIBRAS_JWT_SECRET` عند غيابه
  يولّد سرًا مؤقتًا مع تحذير (يُستخدم للتطوير فقط).

### حدّ المعدل
- متغيرات `NIBRAS_*_RATE_LIMIT_*` لاعتدال المصادقة (نقاط الدخول العامة)،
  الإعلانات، AI، والمجتمع — مُطبقة في المسارات المقابلة.

## ما أُضيف في هذه المرحلة (المراجعة الاستباقية)
- رؤوس أمن على كل الاستجابات (انظر `app/__init__.py`):
  `X-Content-Type-Options: nosniff`، `X-Frame-Options: DENY`،
  `Referrer-Policy: strict-origin-when-cross-origin`،
  `Permissions-Policy: camera=(), microphone=(), geolocation=()`.
- سجلّات مهيكلة مع تعمية الحقول الحساسة (`password`, `token`,
  `authorization`, `secret`, `api_key`, `email`, …) في `app/logging_utils.py`.
- معرّف طلب `X-Request-ID` مُصدَر للتعقّب وربط السجلات.
- `/api/ready` للجاهزية (فحص اتصال قاعدة البيانات) + معالج 500 يسجّل
  `unhandled_error` بكامل traceback دون كشفه للعميل.
- نسخ احتياطي/استعادة موثّق (انظر `scripts/backup.py`).

## نتائج اختبار الحمل/الإجهاد (أساس)
تشغيل `scripts/load_test.py` على نسخة مؤقتة من قاعدة البيانات (خادم dev
`werkzeug` threaded، جهاز واحد):

| الإعداد | النتيجة |
|---------|---------|
| تسلسلي (1 متزامن) | ~10–12ms متوسط، p95 ~15–28ms |
| 32 متزامن / 1000 طلب | **100% نجاح**، ~100 طلب/ثانية، p50 ~302ms، p95 ~461ms |
| 64 متزامن / 1500 طلب | **1500/1500 نجاح**، لا 5xx، p95 ~710ms |

الخلاصة: الخادم مستقر بلا أخطاء أو تسرّب استثناءات؛ تدهور زمن الاستجابة مع
التزامن متوقع لخادم dev أحادي العملية + GIL + اتصال SQLite لكل طلب. للإنتاج:
نشر خلف خادم WSGI متعدد العمال (مثل gunicorn) مع HTTPs عبر وكيل عكسي.

## بنود مؤجلة (توصيات مراحل لاحقة / إنتاج)
1. **CSP**: رأس Content-Security-Policy يحتاج جرد نطاقات الواجهة — مؤجل حتى
   تحديد أصله في الإنتاج.
2. **تثبيت IP + إشعار**: بعد عدة محاولات دخول فاشلة من نفس IP، ولوحة إدارة
   للجلسات النشطة.
3. **تشفير الملفات ساكنة**: فولدر uploads/ بمفاتيح خارجية (أو SQLCipher
   لقاعدة البيانات) — قرار معماري مؤجل.
4. **إعادة توجيه HTTPS/معايير TLS**: تُفرض في طبقة الوكيل العكسي لا التطبيق.
5. **سياسة استبقاء سجلات**: نافذة تدقيق + دورة حياة لفولدر backups (الاحتفاظ
   الافتراضي 7 نسخ عبر `--keep`).
6. **تكامل SCIM/SSO** مستقبلًا لنهايات OIDC إن تطلّب النشر المؤسسي.
